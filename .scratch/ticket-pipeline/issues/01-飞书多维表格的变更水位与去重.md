### 1. 变更水位算法

**身份用 `record_id`，不用「序号」列。** 序号是人手填的、会被改、会因插行/删行重排、前两行还是示例行 —— 不能当主键。`record_id` 由飞书生成、稳定、删除后不复用。

**扫描方式**：`POST /open-apis/bitable/v1/apps/{app_token}/tables/{table_id}/records/search`

- `page_size: 500`（上限），`automatic_fields: true`（拿自动维护的 `last_modified_time`）
- **排序**：`sort: [{ field_name: "最后更新时间", desc: true }]`，从最新往回翻
- **不能用 `ExactDate` 过滤**：它被截断到「天」，同一天内的变更分不出来。只能客户端逐页比对。

**水位结构**（存 `storageDomain`）：

```ts
type Watermark = {
  // 见过的 record 及其内容指纹；水位判断的真相在这里，不在单一时间戳上
  seen: Record<string /* recordId */, { mtime: number; fingerprint: string }>
  lastScanAt: number          // 上次扫描完成时刻（ISO 毫秒），用于诊断
  safePageRun: number         // 连续「全部已知且未变」的条数，见停止条件
}
```

**增量算法**：

1. 从第 1 页（最新）开始拉，逐条比对：
   - `record_id` **不在** `seen` 里 → **新票**（首次出现，无论 mtime 多早）
   - 在 `seen` 里且 `mtime > seen[id].mtime` → **变更**，重算指纹，指纹不同才算真变化
   - 在 `seen` 里且 `mtime == seen[id].mtime` → 未变，`safePageRun++`
2. **停止条件**：`safePageRun >= 20`（连续 20 条都是已知且未变）时停止翻页，而不是「见到第一条 ≤ 水位就停」。
3. 扫描结束把本轮见到的所有 record 写回 `seen`，更新 `lastScanAt`。

**为什么不用「第一条 ≤ 水位就停」**：`last_modified_time` 是服务端维护的，批量操作、导入、跨时区写入都可能让**后改的记录 mtime 反而更早**（乱序）。单点水位会漏票；连续 N 条安全窗口能兜住这种乱序，同时把稳态扫描成本压到 1~2 页。

**首次全量**：`seen = {}`，第一轮把所有 `是否处理 = 处理中` 的行全收进来（同时记录 `是`/`否` 的行到 `seen` 但标为「不跟踪」，避免下一轮把它们当新票），然后写 `seen` + `lastScanAt`。

**删除行**：扫描看不到已删除的记录（它从结果集消失了）。对 `seen` 里存在、但**连续 3 轮扫描都没出现**且状态属于跟踪中的记录，标 `phase = gone`，静默退役（不通知、不删历史）。之所以要 3 轮而不是 1 轮：单轮可能因为分页边界或瞬时 API 异常而看不到。

### 2. 收票筛选

**只认 `是否处理 = 处理中`，不叠加任何其它条件**（用户拍板）。理由：人把状态拨到「处理中」就是明确的开工信号；再叠「处理人为空」会把别人认领后又放弃的票永远卡死，叠「处理人 = 某人」又要在表里维护一份隐式约定。

`是否处理` 是下拉字段，API 返回形状不固定（可能是 `{ text: "处理中" }`、`[{ text: "处理中" }]`、纯字符串），适配器里必须做规范化后再判等，不能直接 `===` 比对象。

三种取值对流水线的语义（这是人给流水线的唯一信号通道，因为表格只读）：

| 取值 | 语义 | 对流水线的动作 |
|---|---|---|
| **否** | 待认领，还没人开工 | **不进流水线**。若此前被跟踪过，标 `gone` 退役。 |
| **处理中** | 明确开工信号 | **进流水线**。新票入队；已跟踪的票按变更处理。 |
| **是** | 已闭环 | **不进流水线**。若此前被跟踪，标 `done` 退役（即使插件自己认为是 failed —— 人以表格为准）。 |

**关键**：因为不回写，「是否处理」从 `处理中` 改回 `否` 或改成 `是`，就是人在说「别做了」/「做完了」。流水线必须尊重，不能因为自己还在跑就无视（见第 3 条的修订语义）。

### 3. 去重与幂等

**跑到一半被改 = 同一条修订，不打断当前运行**（用户拍板）。机制：

- 每次收票算**内容指纹**：`sha256(问题描述 ‖ 模块 ‖ 操作流程 ‖ 截图 ref 列表的规范化串 ‖ 优先级 ‖ 发现部门)`。不把 `是否处理`/`处理人`/`处理结果`/`处理日期` 计入（这些是人的管理字段，不是工单内容）。
- 指纹没变 → 同一份输入，**绝不重复跑**。
- 指纹变了 → `revisionCount++`，作为**修订**排到队尾；当前正在跑的那一版继续跑完，不中断（中断会让人已经等了一半的活白扔，也让 agent 半路丢上下文）。
- 修订跑完的通知文案要带「第 N 版」，人一眼能看出处理的是哪一版。

**幂等键** = `record_id + fingerprint`。用它做存储层主键，重复入队天然被吸收。

**重启恢复**：每票落一行

```ts
type TicketState = {
  recordId: string
  fingerprint: string
  revisionCount: number
  phase: Phase
  worktreePath?: string
  startedAt?: number
  attempt: number
  lastError?: string
}
```

启动时扫一遍：`phase ∉ { done, failed, skipped, gone }` 的票从**当前 phase 往后**接着走，不从头重跑（worktree 还在就用它，不在就从 `worktree-ready` 重来）。`attempt >= Config.maxAttempts` → 标 `failed` + 通知。

### 4. 多进程抢同一行

**用存储层的租约 + CAS，不用文件锁**（文件锁在跨进程/跨用户/网络盘上不可靠，且 `flock` 在 Windows 上语义不同）。

```ts
type Lease = {
  recordId: string
  ownerToken: string      // 实例唯一 ID（启动时生成 UUID）
  leaseExpiresAt: number  // ISO 毫秒
}
```

- 认领：读当前 `Lease`（没有或已过期）→ 写入自己的 `ownerToken` + `leaseExpiresAt = now + 10min`；写完**回读校验**自己的 token 还在（两个实例同时写时后写者胜，先写者回读会发现被覆盖 → 放弃）。
- 续租：每 60 秒把 `leaseExpiresAt` 推后 10 分钟；只在持有租约时续。
- 释放：票跑完（任何终态）立刻清租约。
- 进程崩溃：租约 10 分钟后自动过期，另一实例可接手；接手后先检查 worktree 是否还在，在就从当前 phase 续。

若 `storageDomain` 没有原生 CAS，就用「单写者 + 回读校验」近似：所有写都带 `expectedOwnerToken`，读回不匹配即视为失败并退让。**绝不假设两阶段写是原子的**。

### 5. 行的稳定标识

`record_id`。已删除的记录保留在 `seen` 里标 `gone`，不删历史 —— 否则人恢复一行时会被当成全新工单重跑，还可能重复开 MR。

### 6. 截图的两种形态

`Ticket.screenshots` 统一成带 kind 的联合类型，**取字节的动作留在适配器里**：

```ts
type ScreenshotRef =
  | { kind: 'attachment'; fileToken: string; name: string; size?: number }  // 单元格内嵌图片
  | { kind: 'path'; path: string }                                          // 共享路径（Windows 盘符 / UNC）
  | { kind: 'url'; url: string }                                            // http(s) 链接
  | { kind: 'unknown'; raw: string }                                        // 认不出的原文

interface TicketSource {
  // 适配器负责把任意形态变成字节；内核只负责 saveImage
  loadScreenshot(ref: ScreenshotRef, signal: AbortSignal): Promise<{ data: Uint8Array; mediaType: ImageMediaType; name?: string }>
}
```

- 附件字段 → `GET /open-apis/drive/v1/medias/{file_token}/download`（Bearer tenant token）
- 本地路径 → `ctx.fs.resolve(path)` + `ctx.fs.readBytes()`
- `http(s)` 链接 → 裸 `fetch`（`ctx.web.fetch` 用不了，它不能带凭据）
- 认不出 / 取字节失败 → 标 `needs-info`，通知人补图，**不阻塞排队**（票继续排队，等人补完再跑；不因为缺图就 fail）

内核拿到字节后统一 `ctx.attachments.saveImage({ data, mediaType, name })` → `ImageBlock{ type:'image', attachment: ref }` → 塞进 `UserMessage.content` → `agent.followup()`。这一步所有适配器共用，不重复实现（依据：`research/image-path.md`）。
