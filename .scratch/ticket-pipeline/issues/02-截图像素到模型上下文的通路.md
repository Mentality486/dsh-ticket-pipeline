## Resolution（research 完成）

报告：`.scratch/ticket-pipeline/research/image-path.md`（723 行，每条结论带 `包名:行号`）。

**一句话结论：没有「给本地路径就能上图」的 API。**

唯一合法通路是五步：

```ts
const ref = await ctx.attachments.saveImage({ data, mediaType, name })   // data: Uint8Array
const block: ImageBlock = { type: 'image', attachment: ref }
agent.followup(createUserMessage({ content: [{type:'text',text}, block], source }))
```

### 确切签名

- `AttachmentStore.saveImage(input: SaveImageAttachment): Promise<ImageAttachmentRef>`，`SaveImageAttachment = { data: Uint8Array; mediaType: ImageMediaType; name?: string }`；批量 `saveImages(inputs)` **all-or-nothing、同序返回**。服务 key 是 `attachments`（`ctx.get("attachments")`，可选依赖，要判 undefined）。
- `ImageBlock = { type: 'image'; attachment: ImageAttachmentRef; offloaded?: true }` —— block 上**没有 base64、没有路径、没有 mime**，全在 ref 里，provider adapter 发请求时才解析成字节。
- `agent.inject(message: UserMessage): void` —— 收**整条 UserMessage**，不是 `ContentBlock[]`。三者差别（`dsh-agent-loop:800-814`）：`followup` = next-turn + 唤醒；`steer` = next-step + 唤醒；`inject` = next-step **不唤醒**。**插件自己起 turn 必须用 `followup`**，否则 agent 不动。
- 读字节：`ctx.fs.resolve(path)` → `ctx.fs.readBytes(target, signal, maxBytes)`。

### 限制（`dsh-attachment-local:895-916`）

mime 只支持 png/jpeg/webp/gif。**两套阈值语义完全不同**：20 MiB/图、20 张/消息、200 MiB 聚合、64 Mpx 解码、8192 单边 → **超限直接抛 `AttachmentError`**（`IMAGE_TOO_LARGE` / `IMAGE_TOO_MANY_PIXELS` / `IMAGE_DIMENSION_TOO_LARGE`）；而 4.19 Mpx / 4 MiB 是**归一化目标，超了自动缩**，不报错。正常飞书截图不会触发前者。

### 降级判定

`ctx.llm.resolveModelInfo(provider, model).inputModalities?.includes('image')` 就是答案。**推荐严格版**（`tool_fs.js:909-917`，`undefined` 即拒）：因为 `deepseek-v4-pro` 根本没声明 `inputModalities` 字段（`llm_deepseek:19-33`），宽松版会放行、然后 adapter 抛 `UNSUPPORTED_CONTENT`。运行时另有自动降级（`llm_index.js:2337`）把图换成 `[image omitted because this model accepts text only; …]`，但短路条件同样漏掉 `undefined`。

### 多图与角色

一条 `UserMessage.content` 里放 N 个 image block 即可，`saveImages` 批量存。**图片只能出现在 `user` 和 `tool` 角色**，其它角色 adapter 显式拒绝。

### tool 返回图 vs 直接 inject

机制上都行（`output.render(): ContentBlock[]` 可返回 ImageBlock，须过 lossless-JSON 检查）。差别：tool 结果进 durable `tool/result` 事件、永远留在历史里、每轮重付视觉 token；inject 是 next-step 一次性上下文。**关键**：`read_image` 工具在 base composition 里**已默认开启**（`base_cordis.patch.yml:295-296` 无 config + `readImage` 默认 true），**插件不需要自己写读图 tool**。

### 需要拍板的三点（留到 05 号票一起定）

1. `source.kind`：`{kind:'user'}` vs 自定义 `{kind:'ticket', ticketId}` —— 自定义**已验证** append/restore 都能过、无消费者抛错（`session_index.js:1194-1223` 只对 system/assistant/tool 强制精确 kind），代价只是不进 UI steering 列表、不更新 `lastPromptAt`。建议自定义。
2. 截图通路：**A** 落盘 + 让 agent 自己 `read_image`（省 context 但 agent 可能不读）/ **B** 首发就 inject（不漏但每轮重付 token）/ **C** 混合（推荐：首发送 1 张主图，其余列路径按需读）。
3. 无 vision 模型时：整票立刻失败 + 微信通知，还是排队等模型切回？建议前者。
