## Resolution（grilling 收口，用户 2026-11-03 确认「都按推荐」）

六问全部定案。以下每条都是**已拍板**的，不是选项。

### Q1 骨架形状 → 四层适配器 + 一个内核

四个可替换原件，内核只认接口、不知道实现：

| 层 | 接口 | 可替换实现 |
|---|---|---|
| 工单源 | `TicketSource` | 飞书多维表格（首个真实）、WPS/金山文档、Mock |
| 仓库定位 | `RepoLocator` | `mgiot-pms` 静态别名表 + 搜索、Mock |
| 执行 | `WorkExecutor` | DSH agent 真跑、Mock |
| 通知 | `PushAdapter` | PushPlus `channel=clawbot`（默认）、企微机器人、Server酱、Mock |

内核 = `Scheduler`（轮询驱动 + 并发闸）+ `TicketStore`（`storageDomain` 状态机）+ `Config`。

**明确不独立成层的两个**：
- **变更检测不是一层** —— 它是 `TicketSource` 实现内部的事（飞书靠 `last_modified_time` 水位、WPS 靠 `mtime`+hash，形态完全不同，硬抽成一层就是假接口）。
- **测试与 MR 不是两个模块** —— 测试是 `WorkExecutor` 的一个阶段，MR 是它的输出物；拆开会让「谁决定要不要开 MR」变得含糊。

### Q2 agent 上下文 → 进程内 `ctx.agents.create()`

```ts
const { agent } = await agents.create({ sessionId, meta: { cwd: worktreePath }, agentOptions, setup })
agent.followup(createUserMessage({ content, source }))
```

**不用**子进程 `dsh --profile headless`：它的两个前置条件在本机都不成立（需可写 `DSH_HOME` + 自备 `DEEPSEEK_API_KEY`，且忽略 GUI 凭据），还要自己解析 NDJSON 才能表达「这一票失败了」。
**不用**混合降级：那是给不存在的场景准备的复杂度。
代价「插件崩 = 在跑的票一起死」由 Q3 的恢复机制兜住，不靠进程隔离。

### Q3 重启恢复 → `storageDomain` 存阶段 + 启动扫描

每票落 `{ recordId, phase, worktreePath, startedAt, attempt, lastError }`。

`phase` 枚举（**必须能表达「上次干到哪一步」**）：

```
pending → worktree-ready → planning → editing → testing → mr-opening → done | failed | skipped
```

启动时扫描所有 `phase != done/failed/skipped` 的票：`attempt >= maxAttempts` → 标 `failed` + 发通知；否则重置为 `pending` 重新排队。恢复从 `phase` 往后接着走，**不从头重跑**。

**明确不用** `ctx.schedule`（持久但绑会话，依赖 Host Web Session 控制器与会话持久化，与本 effort「插件常驻、不依赖某个聊天会话」冲突），也**不做**「崩了就等下次轮询当新票重跑」（会重复开 MR，虽 409 能挡，但 worktree 会越积越多）。

### Q4 轮询驱动 → `ctx.timer.interval` 为唯一默认入口 + 手动触发兜底

- 定时器间隔来自 `Config`，默认 **3 分钟**（对应 map 的 3~5 分钟）。
- 同时注册 `pipeline_scan` 工具与命令供人手动敲一次（`ctx.tools.register` + `ctx.commands.register`，几乎零成本；调试和「刚填完想立刻看效果」时需要）。
- **启动恢复里要顺带 `ensureTimer()`** —— 否则进程起来了但 timer 没被重排（如插件热重载）就静默不跑了。

### Q5 每票 agent 策略 → 每票新建，复用同一套 `agentOptions`

- 每票 `agents.create({ cwd: worktreePath })`，干完就丢。
- 稳定知识（「你在 mgiot-pms 里、先读 AGENTS.md/CLAUDE.md、测试跑 `mvn -o test`、模块别名表」）用 `ctx.systemPrompt.section()` 做成常驻段，每票只注入工单内容 + 截图。

**不用**长驻复用单 agent：上下文会被上一票的代码细节污染（第 50 票还记得第 3 票改过什么，既费 token 又可能误改），且并发 1 时一票失败会拖垮后续所有票。
**不用**裸新建不共享 prompt：每票都要重讲一遍规则。

### Q6 超时裁决 → `ctx.timer.timeout` 包整票 + cancel + 保留 worktree 24h

超时 → `agent.cancel()` + 标 `failed` + 发通知，**worktree 保留 24 小时**再清（`Config.worktreeRetentionHours: 24`）。

**不用**只告警不杀：卡死的票会永久占住唯一并发槽（并发 1），流水线直接停摆。
**不用**杀完就删 worktree：超时最需要看的就是「它当时改到什么程度」。

### 落到实现上的接口草案

```ts
interface TicketSource {
  id: string                                  // 'feishu' | 'wps' | 'mock'
  scan(signal: AbortSignal): Promise<Ticket[]>   // 水位之后的票
  // 无 writeBack：表格只读（用户已决定）
}

interface RepoLocator {
  locate(ticket: Ticket): Promise<LocateResult>  // { repoPath, module, candidatePaths[], ambiguous }
}

interface WorkExecutor {
  run(ticket: Ticket, plan: Plan, ctx: ExecCtx): Promise<ExecResult>
  // ExecResult: { phase, changedFiles[], testOutcome: 'passed'|'failed'|'skipped', artifact }
}

interface PushAdapter {
  id: string
  send(msg: { title: string; body: string; link?: string }): Promise<{ accepted: boolean; traceId?: string }>
}
```

`PushAdapter.send` 的 `accepted` **不等于送达** —— PushPlus 的 `code:200` 只代表受理，送达要看 `callbackUrl` 的 `sendStatus`（0未发/1发送中/2成功/3失败）。这条写进适配器契约注释。

## Answer

grilling 收口（用户确认「都按推荐」）：四层适配器 + 内核；agent 走进程内 agents.create；重启靠 storageDomain 的 phase 状态机恢复；timer.interval 为默认驱动 + 手动触发兜底；每票新建 agent 但复用 systemPrompt 段；超时 cancel 并保留 worktree 24h。
