# ADR-0004：插件里的 git / verify 显式申请完整文件系统权限

状态：已采纳（2026-11-04）

## 背景

插件跑票要在目标仓库里做 git 写操作（`fetch`、`worktree add`、`commit`），也要跑项目配置的
`verify` 命令。实测这些都稳定失败：

```
internal: git fetch 失败：error: cannot open '.git/FETCH_HEAD': Permission denied
```

而同一条命令、同一路径、同一用户，在 DSH 的 bash 工具里**成功**。`icacls` 上目标目录与
`.git` 只有继承的允许项、没有 DENY —— 所以既不是 ACL 错也不是路径错。

读宿主 `app.asar` 源码得到真机制：插件调 `shell.execute(shell.resolve({ command }))` 时
没传 `sandboxPolicy`，宿主 `SandboxBashExecutor.resolve` 退回
`ctx.sandboxPolicy.resolve()`。插件不是会话，这个调用**没有 `session`**，于是
`SandboxPolicyService.resolve` 返回的策略里没有 `sessionId`；Windows 的
`windowsAclRunnerArgv(policy)` 在 `sessionId === undefined` 时**一个写授权 SID 都不发**，
子进程只剩受限令牌 + Low 完整性 → 写 `.git/FETCH_HEAD`（lockfile + rename）必被拒。

工具 bash 能成，是因为它走会话策略，而 `SandboxBashExecutor.execute` 在
`mode === 'danger-full-access'` 时直接本地执行、完全跳过 confine。

## 决策

1. 组合根导出 `fullAccessSandboxPolicy(cwd)`，返回
   `{ mode: 'danger-full-access', workspaceRoot: <绝对路径> }`，
   **所有**走宿主 shell 的调用点显式传它（`makeGitRunner`、`makeCommandRunner`）。
   不依赖部署默认值 —— 默认值随会话而变，插件拿不到会话。
2. `workspaceRoot` 必须是绝对路径（宿主 `resolveWorkspaceRoot` 只认绝对路径，相对路径抛
   `sandbox-policy: workspace root must be an absolute execution-world path`），
   因此函数内有绝对路径守卫，判不出来时回退 `process.cwd()`。配错的 cwd 应该在
   「仓库不存在」这种业务错误里暴露，不该在策略层炸成看不懂的错。
3. 这条旁路**只给 git 与 verify 用**。执行模型生成的任意 shell 不走这里
   （`executor-agent` 有自己独立的命令通道）。

## 后果

- 插件在任何会话策略下都能写目标仓库，跑票不再依赖「用户恰好把会话设成 danger-full-access」。
- **代价必须写进使用手册**：跑票期间那两个子进程有完整文件系统权限。使用者在
  `docs/ticket-pipeline/user-guide.md` §5.3 能看到这条，不只是藏在代码注释里。
- 这条决策把「安全边界」从「靠宿主默认」变成「插件声明的、可审计的行为」：
  想收紧只需改这一处，而不是去猜每个部署的默认策略。
- 反面约束：新增任何 shell 调用点，**必须**同样传策略，否则会在那台机器上莫名其妙地
  `Permission denied`。自测 `dev-run.mjs` 第 12c 节对此有断言（检查 resolve 请求里带没带策略）。
