# ADR-0006：处理完回填工单表

状态：已采纳（2026-11-06）——**推翻了 ADR-0001 时期「表格只读」的口径**

## 背景

从 v0.1 到 v0.1.0-test.1，插件一直把「工单表只读」当硬约束写进契约、架构、自测三处：

- `src/contracts/ticket-source.js` 的 `TicketSource` 文件头：「`scan` **不得**写任何远端状态（表格只读，这是用户拍板的硬约束）」；
- `docs/ticket-pipeline/architecture.md` §1 约束表「工单表 **只读**，绝不回写任何列」、§12.6「明确不做」第 5 条；
- `scripts/feishu-checks.mjs` 有一条断言盯着「扫描全程只允许出现 `GET` / `POST /auth/...` / `POST /records/search` 三种请求」。

用户 2026-11-06 改了口径（原话）：

> 改完工单需求之后 需要回填将处理中改为 是 并回填处理结果和处理日期 处理结果填怎么处理的。

理由是人肉环节的痛点：票跑完之后表格里那一行还是「处理中」，处理结果和处理日期都空着。
人要自己去 `pipeline_status` 或通知邮件里找 sha、找改了什么，再手工往表里抄一遍。
插件明明已经知道全部信息（改了哪些文件、验证过没有、提交 sha、会话在哪），
不回填等于把整理成本留给了人。

## 决策

### 1. 扫描仍然只读，写只有一个入口

`TicketSource` 新增**可选**方法：

```ts
writeResult(recordId: string, result: WriteBackResult, signal: AbortSignal): Promise<WriteBackReceipt>

type WriteBackResult = { status?: string, result: string, handledAt?: number }
type WriteBackReceipt = { written: boolean, fields?: string[], note?: string }
```

`scan()` 的行为一个字节不改。契约文档改成：「`scan` 不得写任何远端状态……**唯一的写入口是
`writeResult`**，它只在票跑完 done/skipped 之后被调用一次，绝不在扫描/重试中间调用。」

这样「只读」的性质还在：**读路径与写路径物理分离，读路径永远不会因为写权限而改变形态**。
适配器不实现 `writeResult` 就是纯只读源（webform 就是这样），`assertTicketSource` 校验它
要么是函数要么不存在。

### 2. 只写 done / skipped，failed 不写

failed 的时候表里那行**保持「处理中」**。这是刻意留的信号：人扫一眼表格就知道这票没成、
还等着重新拨进队列。要是 failed 也写个「是」，等于替人做了「这票处理完了」的判断，
而实际上它一个字都没改。

### 3. 回填失败绝不影响票态

表格写不进去是网络 / 权限 / 表结构问题，不是这张票白干了。所以 `writeBackFor()` 里
**所有异常都被吞成 `{written:false, note}`**，票该是 done 还是 done。原因记在
`writeBack.note` 里，`pipeline_status` 会显示「回填表格：没写成 —— …」。

同理，表里没有这三列（用户表结构不一样）时适配器返回 `{written:false, note}` 而不抛。
`FIELD_MISSING_ERROR_CODES = new Set([1254040, 1254045])` + `isFieldMissingError()`
按「错误码 / `FieldNameNotFound` / 文案里有『字段…不存在』」三种证据判定。

> **2026-11-10 修订（ADR-0007）**：「票态不回退」这一点保持不变，但**失败不再等于终局**。
> 原来失败既不留待办也不重试，导致真机上「回填失败了」这件事在存储里彻底消失。
> 现在回执要标 `retryable`：可重试的留待办、下次启动补做一次；不可重试的
> （同步表 / 少列 / 电子表格缺列或只有读权限）当场放弃并记进 `delivery.writeBack.giveUp`。
> 详见 `docs/adr/0007-交付维度.md`。
>
> **2026-11-10 再修订（工单 #22）**：「电子表格不回填」这一条已经作废 —— 电子表格
> 现在也写回那三列（失败票只写「处理结果」那一格）。原因不是加功能，而是只读会让
> 「是否处理」永远停在「处理中」⇒ 下一轮把同一张票再收一遍。代价：应用需要
> `sheets:spreadsheet`（读写）而不是 `:readonly`。见 `docs/adr/0005-飞书电子表格源按表型分派.md` 的修订节。

### 4. 被取消就不写

`signal.aborted` 时直接返回 `{written:false, note:'这张票被取消了，按约定不回填表格'}`。
人按了取消，说明他不想这条链路再动任何远端状态。

### 5. 开关是配置项，不写死在代码里

- `writeBack`（boolean，缺省 `true`）：关掉就完全不碰表格，退回纯只读。
- `writeBackStatus`（string，缺省 `是`）：有的表用「是」，有的用「已完成」「已处理」。
  硬编码一个值等于把配置问题变成改代码问题。

### 6. 「处理结果」列写什么由 `renderWriteBackResult()` 决定

写给**人**看的，不是写日志。顺序按人的关心程度排：改了什么（最多 8 个文件）→ 验证过没有
→ 提交 sha 在哪 → 会话在哪 → 怎么重跑。末段固定一句
「要进一步修改，把这个单元格清空、把「是否处理」拨回「处理中」即可重跑。」

刻意不写进表格的东西：完整改动 diff、编译输出、内部错误栈。表格单元格塞几千字没法读。

## 代价与已知限制

- **飞书应用需要写权限**。当前实测的应用对该表**只有读权限**，写回会返回
  `code 91403 Forbidden`。这时票仍是 `done`，只是 `writeBack.written === false`。
  要真正用起来，得去开放平台给应用加「编辑」权限。
- 回填是**一次调用、不重试**。表格 API 抖一下就没写入，只能靠 `pipeline_status` 看见
  「回填表格：没写成」然后人工补。理由：票已经交付完了，为了一个单元格把整条链路
  拖进重试队列不划算。

  > **2026-11-10 修订（ADR-0007）**：这一条被收窄了。现在**可重试**的失败（网络 / 限流）
  > 会留待办、下次启动补做一次；**不可重试**的仍然一次就收手。仍然不进跑票队列的退避 ——
  > 回填的失败面主要是权限与表结构，不是抖动。
- 三列列名硬编码在飞书适配器里（`FEISHU_COLUMNS` 已有的那三项）。表结构不同的用户
  要么改表头，要么关掉 `writeBack`。
- 指纹刻意不含 status / 处理人 / 处理结果 / 处理日期（见 `FINGERPRINT_FIELDS`），
  所以**回填不会触发「修订」死循环** —— 这是回填能安全落地的前提，改指纹字段前必须
  重新考虑这件事。

## 决策 2 的修订（2026-11-10，工单 #14）

### 原来怎么定的，为什么

决策 2 写的是「只写 done / skipped，failed 不写」，理由是「failed 时表里那行保持『处理中』
是刻意留的信号：人扫一眼表格就知道这票没成」。

这条理由本身没错，但它只考虑了**一个人、盯着表格**的情形。

### 改的原因

真实案例：`docs/ticket-pipeline/feature-checklist.md` §1.19 记录三张 sandbox 票
在表里躺了三天没人发现。原因不是谁疏忽，是**两套界面状态对不上**：

- 人在飞书表格里工作，插件在 GUI 里工作；
- 表里「处理中」这一个值，在飞书 UI 里同时代表「正在被处理」「还没开始」「已经失败了没人管」；
- 插件侧 `pipeline_status` / 通知邮件说得再清楚，人只要不在 GUI 里就看不见。

也就是说，「留在处理中是刻意留的信号」这个设计与现实相反：**它不是一个信号，是一个噪音**。
真正能当信号的是「处理结果列里有话」—— 人一眼看到的是失败原因，而不是一个没有信息量的「处理中」。

### 折中方案

新增配置项 `writeBackOnFailure`（boolean，**缺省 `false`**）：

| | 缺省（false） | 打开（true） |
|---|---|---|
| `done` / `skipped` | 三列都写（原样） | 三列都写（原样） |
| `failed` / `needs-info` | 完全不写 | **只写「处理结果」一列** |
| `gone` | 完全不写 | 也不写（见表里那行已被删了，写必然 404） |
| 「是否处理」列 | — | **绝不写**，保持「处理中」 |
| 「处理日期」列 | — | **绝不写**（那是人的字段） |

「处理结果」里写的是给人看的四件事：为什么没成、工作区在哪、会话在哪、怎么重跑
（由 `renderFailureWriteBack()` 生成，与成功回填的 `renderWriteBackResult()` 是**两个函数、
同一个写入通道** —— 飞书单元格是整格覆盖，所以覆盖天然幂等）。

超时的票也写（人不在电脑前，表里那行停「处理中」正是他最需要看到的）；
**人工取消的不写** —— 人主动喊停，说明他不想让这条链路再动任何远端状态。

### 对「人只做三件事」这个价值主张的影响

它是**补上**了第三件事（「看结果」）的可操作性，而不是削弱。原来人只能在 GUI 里看结果，
而失败票的结果恰恰是最需要被看到的；现在失败票也会在表格里说一句话，
人仍然不用打开 GUI 就知道「这票卡在哪、下一步做什么」。

### 为什么不缺省打开

会让老用户升级后表格里突然多出内容 —— 那是行为变更，不是修 bug。缺省关、写清楚它做什么、
想用的人自己开。

### 与决策 3（回填失败不影响票态）的关系

完全继承：失败回填本身失败（比如这张表是同步表）时，票态仍然是 `failed`，
不因为「回填没写成」而变成别的状态；失败分档走 ADR-0007 的 `delivery.writeBack`。
