# ADR-0005：飞书电子表格源按表型分派

状态：已采纳（2026-11-06），**已实施**（2026-11-09）

## 背景

用户 2026-11-06 提出需求：「能否都支持 由插件判断用户使用的是多维表格还是电子表格选择特定的工单」。

插件的飞书源（`plugins/ticket-pipeline/src/adapters/source-feishu/index.js`）目前只认**多维表格（Bitable）**：

- 绑定键是 `appToken` + `tableId`，扫描走 `POST /open-apis/bitable/v1/apps/:app_token/tables/:table_id/records/search`；
- 行身份是平台给的 `record_id`（`index.js:971`）；
- 变更判定同时看 `mtime`（`pickMtime`，`index.js:894-906`）与内容指纹；
- 早停机制是「连续 `safePageRun` 条已知且未变就停翻页」（`index.js:1004-1005`、`:1031-1034`）。

**电子表格（Sheets）在这四点上都不同**，而且不是「少几个字段」的程度：

| 维度 | 多维表格 | 电子表格 |
| --- | --- | --- |
| 绑定键 | `appToken` + `tableId` | `spreadsheetToken` + `sheetId` |
| 读值接口 | `records/search`（**有分页**，`has_more` / `page_token`） | `sheets/v2 .../values/:range`（**无分页**，响应里根本没有这两个字段；单次上限 10 MB） |
| 行身份 | `record_id`（平台生成，稳定） | **没有** —— 必须自造 |
| 行级 mtime | 有（`last_modified_time`） | **没有** |
| 元数据接口 | `bitable/v1 .../tables` | `sheets/v3 .../sheets/query`（**snake_case**，与 v2 读值接口的 camelCase 不是一套风格） |

当前代码把这条路彻底堵死了，而且堵得很「硬」：`index.js:763-766` 的 wiki 节点查询把 `obj_type: 'bitable'` **硬写进 query**，`:770-775` 于是把 `sheet` 判成「不是多维表格」并抛错，错误文案里还写着「sheet=电子表格」不支持 —— 这不是权限问题，是代码路径问题。

同时 `src/core/config.js:494-501` 的配置校验要求飞书项目必须给「`appToken`+`tableId`」或「`docNamePattern`」二选一，只给 `spreadsheetToken` 的配置在启动时就被拒。

## 决策

1. **不新增 `platform`，表型由插件探测。** `PLATFORMS`（`config.js:447`）是**平台**表（ADR-0001），而 bitable / sheet 是**同一平台下的两种文档类型**。加进平台表意味着组合根、`SOURCES`、`validateProject` 三处都要动（ADR-0001 说的「加平台成本」），而且违背用户「由插件判断」的要求 —— 表型变成人填的配置项，判断责任就推回给人了。

2. **探测按 token 形态分三种走法，结果缓存整轮。**
   - wiki 链接 / wiki token → `GET /open-apis/wiki/v2/spaces/get_node` **不带** `obj_type`，读 `node.obj_type`：`bitable` → 多维表格分支，`sheet` → 电子表格分支。官方已确认电子表格的 `obj_token` 同时就是 `spreadsheetToken`，不需要二次换算。
   - 裸 token → 先试 bitable 表清单，失败再试 sheet 工作表清单。
   - 只有 `docNamePattern` → `drive/v1/files` 搜索扩到 `type ∈ {bitable, sheet}`，合计命中恰好 1 张才用；命中多张（如一张 bitable + 一张 sheet 同名）当**配置错误**，不瞎猜。
   - 探测结果存进 `tableCache`，形状升级为带 `kind` 的联合类型；一轮扫描只探测一次。

3. **探测阶段的错误必须按「与表型无关」分流。** `auth` / `rate-limit` / `network` 类错误**直接抛**，不换接口重试 —— 凭据、限流、网络问题与表型无关，换个接口再试只会把真因埋掉。只有 `not-found` / `invalid-input` 才继续试另一种表型。

4. **电子表格的行身份自造，默认用序号列，物理行号兜底。**
   - `match.sheetIdentity: 'seq'`（默认）→ `sh-seq-<序号列的值>`；
   - `match.sheetIdentity: 'row'` → `sh-row-<物理行号>`；
   - 序号为空 → 兜底成行号，并在 `raw.identitySource` 标 `fallback-row`（**两种来源必须能区分**，否则同一张票在水位里身份漂移）；
   - 同一轮序号重复 → 报 `invalid-input` 并列出重复值与行号，**不静默取第一个**（静默取第一个 = 一张票吞掉另一张）。

   代价已知且接受：插行会让行号身份整体漂移（旧票退役 + 新票涌入），序号被重填也会换身份。金山源已经踩过同一个坑（`source-wps/xlsx.js:611-613` 的注释明确写了这个取舍），电子表格分支**继承同一套水位与退役语义**，不另造机制。

5. **电子表格分支不做早停。** `safePageRun` 早停的依据是「按 mtime 降序翻页」，而电子表格既没有行级 mtime，读值接口也**没有分页协议**。强行早停等于自己发明分页。所以改成「一次读全表 + 逐行指纹比对」，靠 `match.sheetRange` 限制读取范围来控制单次 10 MB 上限。

6. **指纹、水位、退役语义与多维表格同源。** `makeTicket` / `fingerprintOf` 一个字都不改 —— 指纹只含工单内容（描述 / 模块 / 操作流程 / 截图 / 优先级 / 发现部门），**不含**「是否处理」等管理字段。差异只有一处：sheet 分支拿不到 mtime，`seen[recordId].mtime` 恒为 0，变更判定完全依赖指纹。

7. **首版截图只支持 `url` 与 `path` 两种形态。** 电子表格的**内嵌图片没有稳定可下载的 token 形态**，一律当「没有截图」。`url` 形态继续走 `match.allowedImageHosts` 白名单（缺省全拒）—— 截图地址是外部输入，这条安全闸门不因为换了表型而破例。

8. **保留 `match.tableKind` 作为逃生阀。** 显式配置时**跳过探测**（省两次请求）；探测失败时错误文案提示「实在判断不了可以显式写这个」。默认不给。

## 后果

- `src/contracts/*`（`TicketSource` 契约、`makeTicket`、`fingerprintOf`）、`src/core/scheduler.js`、`src/core/store.js`、`src/index.js`（`SOURCES` / `PLATFORMS` / `buildSourceOptions`）**一个字都不用改**。这是「不新增平台」这个决策的直接红利。
- 代码落点：新增 `src/adapters/source-feishu/sheets.js`（探测的 sheet 分支 + 工作表定位 + 读值 + 表头映射 + 身份计算），`index.js` 只做分派 —— 与金山源同构（`source-wps/index.js` + `source-wps/xlsx.js`）。
- 配置面新增 9 个项目级键（`spreadsheetToken` / `sheetId` / `sheetName` / `sheetHeaderRow` / `sheetIdentity` / `sheetIdColumn` / `sheetColumns` / `sheetRange` / `tableKind`），全部「写了才透传」，不给缺省值。其中 **`sheetName` 与金山源共用同一个键**（语义一致：这张文档里用哪个页签），不新增第二份定义。
- 人工前置要单独开一套 scope：`sheets:spreadsheet:readonly`（或 `drive:drive:readonly`）与多维表格的 `bitable:app:readonly` **互不相通**；且电子表格所有者仍要手动「添加文档应用」授权（`POST /drive/v1/permissions/:token/members` 只对 `user_access_token` 有效，插件用的是 `tenant_access_token`）。
- 已知代价写进文档而不是藏着：插行漂移、无 mtime、无分页、内嵌图不支持。

详见 `docs/ticket-pipeline/feishu-sheet-source.md`（设计与实施记录，§12 是实施结果）。

## 实施后的补充（2026-11-09）

实测多出两条决策 3 没覆盖的情形，已落进代码，记录在此避免后人重新踩：

1. **「已确认是多维表格」也是一种不该换接口的理由。** 决策 3 只按错误类别分流（auth / rate-limit / network / internal 不换）。实施时发现还有一种：`resolveBitableTableByIdentity` 已经把数据表清单读回来了、只是 `docNamePattern` 匹配不上 —— 这**证明** token 就是多维表格，换 sheet 接口重试只会把「表名写错了」这个真因埋掉。做法：抛错对象上打 `confirmedBitable = true`，`shouldTrySheet` 见到就返回 false。
2. **`docNamePattern` 只用来挑云文档，不再用来过滤数据表名。** 第四步（只有 `docNamePattern` 时）调用 `resolveBitableTableByIdentity(token, signal, false)` 显式关掉 `usePattern`；否则同一个 pattern 会同时被用在「云文档名」和「数据表名」两个层级，通常是 0 命中。这条是自测第一次跑红出来的。

另外：`sheetName` 与控制面板的关系比预想的麻烦 —— 它必须**在面板里只画一次**。金山组和飞书组各画一次会变成两个输入框绑同一个草稿键（`client-check` 直接报「重复字段：match.sheetName」），最终落在 `match` 组共用。
