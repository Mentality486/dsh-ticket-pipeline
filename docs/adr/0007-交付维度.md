# ADR-0007：交付维度（`delivery`）与回填失败的分档处理

状态：已采纳（2026-11-10）——**修订 ADR-0006 的决策 3 与「回填一次调用、不重试」那段**

## 背景

真机上有一张票（`reczz28VYQARkYBL`）：代码改完了、验证过了、本地提交有了、通知也发出去了，
**只有回填表格失败**，飞书返回：

```
800074911：ConnectorSyncTableActionForbidden,
[status_code: 800004105 msg: syncTable can not apply action:action=data.setRecord,
 tabID=tblWhRSGf0osJqrE, fldID=fldfZLT0D6]
```

而插件把整票判成**成功**，`pipeline_status` 显示「已完成」，人从任何界面都看不出
「表格里那一行还停在『处理中』、处理结果永远空着」。

根因不是「漏打一条日志」，是**模型少了一维**：

- `phase` 答的是「流程走到哪一站」。`done` 只说明执行器认为活干完了。
- 没有任何字段答「该交给人的东西交到了没有」。

三条交付各有各的失败方式，且**都不改变 `phase`**：

| 交付项 | 可能的失败 | 原来记在哪 |
|---|---|---|
| `commit`（可 review 的改动） | 执行器说 done，却既没有本地提交也没有 MR | 哪儿都没记 |
| `writeBack`（表格三列） | 网络抖 / 无写权限 / 同步表 / 少列 | `writeBack.written=false`，但**被当成成功**，且补做标记被无条件清掉 |
| `notify`（通知） | 邮件服务挂、token 过期 | 只 `logInfo`，连回执都没有 |

更糟的是 ADR-0006 时期的两处实现：

1. `scheduler.js` 里 `if (writeBackPlanned) await clearPendingEffect(key, 'writeBack')`
   **无论成败都清**。于是 `replayPendingEffects()` 永远捞不到这张票 —— 它不是「还没做」，
   而是「做过了、失败了」，而模型里没有第三种状态。
2. `writeBackFor()` 的 catch 把错误写成 `` `${reason.kind}: ${reason.message}` ``，
   于是人看到 `internal: 飞书接口报错 800074911…`。**`800074911` 是配置问题**（表是同步表，
   结构上不接受写记录），却被标成 `internal` —— 而 `internal` 在 `RETRYABLE_KINDS` 里，
   意思是「值得重试」。若将来加了重试，就会对着这张表无限撞下去。

另外 `errors.js` 的三张分类表本身有洞：`aborted` 既不在 `RETRYABLE_KINDS` 也不在
`FATAL_KINDS`，分类是空的。

## 决策

### 1. 新增与 `phase` 正交的 `delivery` 维度

落在票据行上，可持久化、可查询：

```js
delivery = {
  commit?:    DeliveryState,
  writeBack?: DeliveryState,
  notify?:    DeliveryState,
}

DeliveryState = {
  ok: boolean
  at?: number            // 这次判定的时刻
  error?: string         // 人话，**不带 kind 前缀**
  errorKind?: ErrorKind  // 分类（程序用，不给人看）
  attempts?: number      // 试过几次
  giveUp?: boolean       // 已放弃：人必须自己动手，别等了
}
```

**为什么不复用现有字段**：`writeBack` 只是回执（写没写成），说不出「放弃了」；
`pendingEffects` 只是「还没做完的事」，说不出「做过了但失败了」；`notify` 彻底是新的。

写入点三处：`runOne` 终态之后（commit）、回填段之后（writeBack）、`notifyFor` 里（notify）。

### 2. 回填失败分两档，`retryable` 是适配器的责任

`WriteBackReceipt` 新增两个字段：

```ts
type WriteBackReceipt = {
  written: boolean
  fields?: string[]
  note?: string          // 人话
  retryable?: boolean    // written=false 时：再试一次有没有意义（**留空视同 false**）
  errorKind?: ErrorKind
}
```

- `retryable: false`（结构 / 配置问题：同步表、少列、电子表格只有读权限、要回填的那一行已被删）：
  再试一百次也是同一个错，**只会让每次启动都撞一遍**。内核当场放弃。
- `retryable: true`（网络、限流、授权码过期）：留着待办、累加 `attempts`，
  下次启动补做一次。

留空按 `false` 处理 —— 宁可少试一次，也不要对着结构上写不进去的表反复报错。

### 3. `clearPendingEffect` 只在「真的做成了」时清

- 写成功 ⇒ 清待办；
- 写失败且可重试 ⇒ **留着待办**并累加 `attempts`，`delivery.writeBack` 记 `{ok:false, giveUp:false}`；
- 写失败且不可重试 ⇒ 清掉待办（不是为了「看起来干净」，而是它确实不会再做了），
  同时 `delivery.writeBack.giveUp = true` 把「人必须自己动手」这件事记下来。

`notify` 同理：以前无条件 `clearPendingEffect(key,'notify')`，于是「通知发不出去」在存储里
彻底消失。现在只有 `delivery.notify.ok === true` 时才清。

### 4. `errors.js` 三张分类表必须互斥且覆盖全部 kind

```js
RETRYABLE_KINDS = new Set(['network', 'rate-limit', 'internal'])
FATAL_KINDS     = new Set(['auth', 'not-found', 'invalid-input', 'unsupported'])
CANCELLED_KINDS = new Set(['aborted'])

export function retryPolicy (kind)  // 'retry' | 'fatal' | 'cancelled'
```

新增 kind `unsupported`：**平台结构上不接受这个操作**（例如往飞书同步表里写记录）。
它和 `invalid-input`（我们传的数据不对）不同：数据没问题，是这条路本来就走不通。
放在 `FATAL_KINDS` 里 —— 重试只会把同一个错误再撞一遍。

自测里有一条断言遍历 `ERROR_KINDS`，逐个检查它**恰好**落在一张表里。

### 5. 用户可见文案里不出现内部标识符

`lastError`、`writeBack.note`、通知正文一律只有人话，分类进 `lastErrorKind` / `errorKind`。
真实影响：真机失败票原来显示 `internal: agent 没有产生任何文件改动`，现在显示
`agent 没有产生任何文件改动`，而 `internal` 在结构化字段里。

### 6. 界面要说清「票完了」与「东西交到手了」的差别

- `pipeline_status` 票标题行加后缀：只有回填失败时是 `（表格未回写）`，
  多项失败时是 `（交付未完成：改动提交、回填表格）`。
- 全库分布下面多一行 `交付未完成：N 张`。
- 逐项列 `交付·回填表格：没做成（已试过 2 次）—— <原因>。<给不放弃还是放弃> `。
- 通知里 `giveUp` 时补一句「这不是再试一次能好的 —— 得你改表格设置」。
- 机器可读：`tickets[].delivery` 原样、`tickets[].deliveryIssues` 只列没做成的项。

## 代价与已知限制

- **票行多了一个字段**，`setDelivery` 是合并写（不是覆盖），所以并发的两处写入不会互相
  抹掉对方。但它和 `setPhase` 一样，不是事务 —— 进程恰好在两次写中间崩掉时，
  `delivery` 可能只记了一半。可接受：缺的那一半下次跑会补。
- **`giveUp` 一旦置上不会自动清**。用户改好表格设置后，要让它重新试，得
  `pipeline_reset` 那张票（或者手工改表把「是否处理」拨回「处理中」）。
  刻意如此：自动重试「已放弃」的项等于让 `giveUp` 失去意义。
- **`retryable` 靠适配器自己判断**，内核不猜。适配器标错（把结构问题标成可重试）
  就会重现「对着同步表反复撞」的老问题 —— 自测里有针对同步表 / 少列 / 电子表格缺列 /
  电子表格只有读权限 / 电子表格那一行已被删 五种不可重试情形各一条断言。
  （电子表格回填是工单 #22 加的，见 ADR-0005 的修订节。）
- 没有做「回填重试的退避」：可重试的回填目前只在**下次启动**补做一次，不进入队列退避。
  理由是回填的失败面主要是权限与表结构（不可重试那一档），网络抖动少。
  真要更积极，应该走与跑票同一套退避，而不是在这里造第二套。
