# 工单流水线插件 · 使用手册

面向**使用者**：从零把插件跑起来，直到收到第一封带**本地提交**的通知，并且知道每天该怎么用它。

> **用词**：本手册统一说「工单」（流水线处理的对象）、「工作区检出」（改代码的那个目录，首次出现括注
> worktree）、「站点」（时间线上的一个阶段）、「适配器」、「回填」。完整对照见 [GLOSSARY.md](../../GLOSSARY.md)。
> `pipeline_status` 等工具的**输出文案**里仍有旧字样「票」，与「工单」同义，属代码产出，未随文档改动。
>
> 配置键的完整清单在 [配置项参考](./reference/config.md)；插件自身开发与自测见
> [插件 README](../../plugins/ticket-pipeline/README.md)；设计取舍见 [architecture.md](./architecture.md)。

## 快速开始

六步。每步都给了「怎么算这步过了」。

### 1. 装插件

最省事的是从 GitHub 直装（不用 clone，不用 GitHub 账号）：

```bash
dsh.cmd --% plugin --profile desktop add "github:Mentality486/dsh-ticket-pipeline#v0.0.1&path:/plugins/ticket-pipeline"
```

`--%` 和 `&path:` 都不能省 —— 前者让 PowerShell 别把 `&` 当命令分隔符，后者告诉 pnpm 去子目录找包（仓库根没有 `package.json`）。

也可以从本地装：`dsh.cmd plugin --profile desktop add "file:<本仓库>/plugins/ticket-pipeline"`。**拿到的不是仓库、而是一个 `.tgz`？** 把 `file:` 后面换成那个文件的绝对路径，其余一样。三种形态的完整装法（含更新、卸载、同版本号覆盖的坑）见 [安装说明](../../INSTALL.md)。

装完**完全重启 DSH 宿主**（桌面包由 Electron 独占管理，刷新页面不算）。**过了没有**：对话里说 `pipeline_status`，工具有响应。

### 2. 填凭据

设置页「凭据」页签，或 DSH 凭据存储，键名一字不差：`FEISHU_APP_ID`、`FEISHU_APP_SECRET`（用飞书工单源时必填）；`QQMAIL_AUTH_CODE`（发 QQ 邮件时）、`PUSHPLUS_TOKEN`（走 PushPlus 时）。**用飞书直发通知不需要额外凭据** —— 它复用上面那对 `FEISHU_APP_ID` / `FEISHU_APP_SECRET`。`GITLAB_TOKEN` **只**在项目打开远程 MR 时才要，缺省不用配。**过了没有**：该页显示「已配置」；`pipeline_doctor` 的凭据行是 ✅。

### 3. 给飞书应用开权限、发布、加协作者

三件都做完才算过，缺一件都跑不出工单：

1. 开放平台 → **权限管理** → 开 `bitable:app`（**读写**，回填要写三列）。
   工单表是**电子表格**的话开 `sheets:spreadsheet`（**读写**，不是 `:readonly`）—— 这是**两套独立**权限。
2. **版本管理与发布** → 创建版本 → 提交发布。**权限不开版本不生效**。
3. 打开那张表 → 右上「…」→「更多」→ **添加文档应用**，把应用加成**可编辑**协作者。
   插件用 `tenant_access_token`，没法自己给自己授权。

**过了没有**：`pipeline_doctor` 的「飞书连通性」节能换到 token、读到表元数据与第一页数据。

### 4. 准备一个本地 git 检出

`repo.path` 指向它，**目录必须已经存在** —— 插件不会替你克隆。它同时就是这个项目的工作区目录（插件会确保它在 DSH 的工作区列表里有一份登记）。**过了没有**：那个目录里 `git status` 能跑。

#### 检出在 WSL 里怎么办

「仓库路径」旁边有两个按钮：**「选择目录」**（系统原生选择器，只看得到盘符）和**「选择 WSL 目录」**（浏览 WSL 发行版里的 Linux 目录）。

检出放在 `\\wsl.localhost\Ubuntu-24.04\home\<你>\projects\xxx` 这种位置时，用第二个：先选发行版，再一层层点进去，最后点「就选这个目录」。填进去的是 `\\wsl.localhost\<发行版>\...` 这个形态 —— **不是** `/home/<你>/...`。原因是插件后续要在这条路径上跑 `git` 与验证命令，Windows 侧的 `git` 只认 UNC 形态。

两点值得先知道：

- 如果那个目录其实在 `/mnt/d/...` 下（WSL 里挂的 Windows 盘），按钮会**自动换算成 `D:\...`** —— 那本来就是 Windows 盘上的路径，走盘符更快。
- 9P 共享比 Windows 盘慢（`git status` 一次约 1 秒），而且 agent 写文件依赖宿主里 `dsh-wsl-folder` 插件那份 9P 写入适配。缺了它，跑票会在改码阶段报 `ENOTSUP`。配置校验**不会拦**你（能跑），只会在体检里给一条提醒说清这些代价。

### 5. 写配置

设置面板：侧栏 Plugins → 「工单流水线」→ 那一行的「配置」。顶部五个页签，缺省停在**运行**：

| 页签 | 干什么 |
|---|---|
| **运行** | 不改配置，用来看事情：开关状态、「跑一轮 / 取消当前 / 刷新状态」、汇总、工单清单（失败的直接点「重跑」） |
| **项目** | 项目清单，可增删、可编辑。缺省只显示常改字段，其余收在「显示全部字段」。每张卡片：`启用这个项目`（关掉=暂停这一个项目）、`工单表链接`、**「测这张表」**（只连一次飞书，验这一张表能不能读，不改任何东西） |
| **参数** | **27 个键 / 4 个分组**（行为 / agent 与模型 / 通知 / 高级），**总开关在「行为」组最上面** |
| **凭据** | 五个凭据键，只写不读回：只显示「已配置 / 未配置」。填完点顶部**「保存」**一次提交；**只填凭据、没改任何配置也能存**（两条通道互不阻塞） |
| **体检** | 与 `pipeline_doctor` 同一份检查，结论分**阻断 / 必须修复 / 提醒** |

**定位工单表只有一个入口：项目卡片最上面的「工单表链接」。** 把工单表的浏览器地址整条贴进去就行，
**不用先分辨它是多维表格还是电子表格** —— 插件自己认表型并取出工单：

- 多维表格 `https://xxx.feishu.cn/base/bascn…?table=tbl…`
- 电子表格 `https://xxx.feishu.cn/sheets/shtcn…?sheet=…`
- 知识库（wiki）里的表 `https://xxx.feishu.cn/wiki/…`（**很多人的工单表在这里**）

写入时宿主会把另一套定位字段清掉（多维表格与电子表格的 token 不会同时留着），所以只有一个框。
`appToken` / `tableId` / `spreadsheetToken` / `sheetId` 这四个 key 面板上都不画输入框、也不下发明文
（宿主只回「已配置（前 4…后 4）」），要手改 YAML 当然可以，但得自己保证不并存两套 ——
并存时校验会给一条「另一套不起作用」的警告。

**「+ 添加项目」的正确顺序**（这一步以前会卡住人）：

1. 点「+ 添加项目」，垫出一张标着「未保存」的卡片；
2. 改项目名（要唯一）、填仓库路径（有「选择目录」与「选择 WSL 目录」两个按钮，也可以手打）；
3. 把工单表链接贴进卡片顶部的框，点 **「记下这条链接」** —— 这时按钮不叫「用这条链接」，
   因为它**不会**立刻写宿主：新项目在宿主里还不存在，写了只会换来一句
   `没有第 N 个项目（当前共 M 个）`；
4. 点顶部 **「保存」**。顺序是「先把项目建出来，再由宿主解析那条链接」。

第 4 步之后如果链接没写进去，只会多一句「项目保存好了，但链接没写进去：…」——
**项目本身是存下来的**，不用再点一次（再点一次会多建一个同名项目）。
已经保存过的卡片就没这个限制，按钮是「用这条链接」，点一下立即生效。

> 点「保存」时，那条链接会**连同项目本身一起**写进配置的 `match.appToken`（三种链接形态
> `/base/<token>`、`/wiki/<token>`、`/sheets/<token>` 运行期各自认得，浏览器不解析它）。
> 保存成功之后插件再调一次宿主把它归一成精确坐标；那一步失败也不影响项目已经存住。
> 所以「贴了链接、填了项目名与仓库路径」之后就该能存进去 —— 如果这时还回
> `feishu 项目必须给①工单表链接/token…`，那是 bug（2026-11-13 修过一版），不是你把链接贴错了。

手改 profile 的 `cordis.patch.yml` 一直有效（**YAML 不是 JSON**，改完**必须重启宿主**），但它不再是任何一步的必经做法。每格在面板上的位置见 [配置项参考](./reference/config.md)。

**过了没有**：面板能保存；`pipeline_doctor` 认到项目与仓库。

### 6. mock 首跑，再切真执行

保持 `workExecutor: mock`、`pushAdapter: mock`，把 `enabled` 打开。在工单表里新建一行：问题描述写「测试：请忽略」，「是否处理」填 `处理中`。等一个轮询周期（≤3 分钟）后 `pipeline_scan` 或点面板的「跑一轮」。

**过了没有**：`pipeline_status` 里出现一张走到 `done` 的工单，表格被回填（不想让它动真表就先关掉 `writeBack`）。

半程通了再切真执行：`workExecutor` → `agent`、`pushAdapter` → `feishu`（或 `qqmail` / `pushplus`），`enabled` 保持开。

**通知适配器怎么选**（`pushAdapter`）：

| 值 | 走哪条通道 | 要先准备什么 | 花钱吗 |
|---|---|---|---|
| `mock` | 什么都不发，只记日志 | 无 | 不 |
| **`feishu`** | **你自己的飞书应用直接发 IM** | 复用 `FEISHU_APP_ID`/`SECRET`；把收件人加进机器人「可用范围」；填 `feishuPush.receiveId` | 不 |
| `qqmail` | SMTP 直发邮件 | `QQMAIL_AUTH_CODE` + `qqmail.user`/`qqmail.to` | 不 |
| `pushplus` | 经 PushPlus 中继到微信 ClawBot | `PUSHPLUS_TOKEN` + **实名认证** | **实名要付费** |

`pushAdapter: feishu` 的 `feishuPush.receiveId` 从哪拿：让机器人**先给自己发一条**，或调 `/open-apis/contact/v3/users`（要有通讯录读权限）拿 `open_id`（形如 `ou_…`）。发不出去时看错误码：`230013` 是**机器人「可用范围」里没有这个人**（去开放平台「应用功能 → 机器人」把人加上，这不是缺权限 scope）；`99991672` 才是真缺权限，报文里会点名缺哪个。

## 日常循环

```
你：在工单表填一行「问题描述 / 操作流程 / 模块 / 截图」，是否处理 = 处理中插件（≤3 分钟内）：收工单 → 确保项目工作区 → 在工作区检出里改代码 → 构建 + 验证 → 本地提交 → 回填三列你：收到通知（判定行 + 提交 sha + 分支 + 失败原因 + 工作区路径 + 处理会话）你：在检出里 `git show <sha>` review → 满意就合到自己的分支，把「是否处理」拨走
```

### 状态怎么看

- **面板「运行」页签**（推荐，不用记命令）：开关状态、汇总（需要你处理 / 待人工验证 / 正在跑 / 已交付 / 已退役）、
  工单清单。失败的工单行尾直接有「重跑」。
  - 这一屏缺省只列**还没收尾**的票（先回答「还要我做什么」）。票全跑完之后那一屏是空的，
    这时候勾上右上角的「**显示历史**」——插件会把已完成 / 已交付 / 失败 / 已删除的票一起列出来，
    每张点开就是完整的九站流程。这个勾选会记住，下次打开还是上次的样子。
  - 票据只增不删，所以历史一直都在，只是缺省不占这一屏。
- `pipeline_status` **不填参数**给的是**按项目聚合的总览**：每个项目一行战报 + 每张工单一行状态
  + **一行流程带**，**永远按全库算**（不会因为筛掉终态就变成「一条都没命中」）。传 `view: "tickets"` 或 `recordId` 看明细。
- 总览里每张工单是两行：

  ```
  · rec-mock-003｜已完成（已验证）｜模块 表单｜最近动静 3 时 14 分前
      取单– 定位✓ 工作区✓ 会话✓ 改代码✓（13 分 42 秒） 验证✓ 提交✓ 回填✓ 通知✓｜全程 13 分 53 秒
  ```

  第一行回答「**现在怎么样**」，第二行回答「**整条路走得顺不顺、哪一站慢 / 哪一站挂了**」。
  九个站点按顺序是 **取单 → 定位 → 工作区 → 会话 → 改代码 → 验证 → 提交 → 回填 → 通知**
  （面板上印的是这九个中文短名，不再是 `①✓②✓` 那种记号 —— 记号要回头翻图例才知道是第几站；
  工具输出里仍是 `①✓`，那里要紧凑）。符号：`✓` 做成 / `✗` 没做成 / `▶` 正停在这一站 / `–` 没走过。
  **失败的票会点名倒在哪里**：`… 提交✗ 回填– 通知–｜✗ 倒在第 ⑦ 站「提交（提交）」｜全程 45 分 34 秒`。
  这一句是补出来的 —— 主站打点恒为「自家这一站 ok」，失败是调度器收尾时另记的，
  所以以前会出现「九站全 ✓ 却标着失败」，人会怀疑自己看漏了哪一格。
  三个刻意的取舍：**只有超过 1 分钟的站才标耗时**（①②③④ 常在 1 秒内，全标反而看不出哪里慢）；
  **跑完的工单最后一站不标耗时**（否则一张昨天跑完的票会显示「⑨发送消息（24 时 32 分）」，像卡在发消息上）；
  **没有流程记录的工单不画一条全 `–` 的带**，直接写「没有流程记录 —— 这张工单的处理早于流程日志功能」
  （画九个 `–` 等于说「插件当时一个站都没走到」，那是假话）。
- 明细里有：**这次改了什么**（文件数、+X/−Y、逐文件清单）、本地提交 sha 与分支、处理会话 id、
  回填结果、交付缺项、最近错误、**流程日志**（逐条带时刻、成败与「上一站花了多久」）。
- **「最近错误」现在是四行，不是一整段原文**：
  ```
  最近错误：提交失败：git 把提交说明里的引号当成了文件名
    为什么：提交说明里带了双引号。插件把这条命令交给 Windows PowerShell 执行时，…
    怎么办：已修复（2026-11-17）…这张票直接「重跑」即可。
    原文：本地提交失败（git commit -m fix(pms): …（原文共 3098 字，已截断）
  ```
  **先看「为什么 + 怎么办」决定要不要动手，需要深挖时再看「原文」**。插件认不出来的错误会明说
  「这条错误插件还认不出来」，并把原文留着 —— 硬套一个像模像样的解释比不解释更坏。

### 通知怎么读

通知**第一行是判定行** —— 手机邮件列表的预览只显示前 1–2 行，所以「要不要你动手」放最前面：

| 判定行 | 什么时候出现 |
|---|---|
| `【不用你做，知道一下就行】` | 已完成 + 验证通过 + 回填成功 |
| `【要你做：去表格里手工回填这一行的「处理结果」】` | 已完成，但回填失败（表格那行还停在「处理中」） |
| `【要你做：这票没跑过验证，请人工验一遍】` | 已完成，但没配验证命令 / 验证没跑起来 |
| `【要你做：改动已交付但验证没过，请人工确认】` | 验证跑过、退出码非零（改动已本地提交） |
| `【要你做：这票失败了】` | 失败 |
| `【要你做：补一张截图】` | 等你补信息 |

正文里：**「已完成」分两种** —— `已完成（已验证）`（验证真跑过）与 `已完成（未跑验证）`（没配 `verify` 或命令没起来）。后者不代表改动不好，只代表没人验过，合并前自己看一眼。失败的通知里也有 `处理会话：<sessionId>`，点进去能看它那一轮到底做了什么。

### 为什么这么慢、卡在哪

- **同一时刻只跑一张工单**：多张工单同时改同一个工作区检出会互相踩，串行是设计不是缺陷。
- `pipeline_status` 有排队时会写四行：`队列：N 张在等` / `下一个是谁` / `排法` /
  `为什么一次只跑一张`。**退避中的工单**单独标「排队中（退避中，还要等 X）」。
- **流程日志**是回答「卡在哪」的那句话：9 个主站（①获取工单 → ②查找项目 → ③检查工作区 → ④创建会话 →
  ⑤处理问题 → ⑥跑验证 → ⑦提交 → ⑧回填 → ⑨发通知）逐条打点，带 `✓/✗` 与「上一站花了多久」。长站点（⑤⑥与规划）**每 60 秒一次心跳**，数字一直往前推就是还活着；`pipeline_status` 直接写「现在停在第 N 站，这一站已经跑了 X」。
- 时间线是**历史**，人工重置不会清空，只在末尾补一条「排队中」分隔。

#### 它会先读很多再动手，现在有两条兜底

一张真实工单实测（2026-11-11）：**第一次写文件在第 46 次工具调用、开始后 21.5 分钟**，
总共 `read 109` 次、`grep 50` 次、`glob 10` 次，只 `edit` 46 次。现在执行器盯两个量：

| 盯什么 | 阈值 | 触发后 |
| --- | --- | --- |
| **停太久**（工作区文件指纹 8 分钟没变） | `agentStallWarnMinutes: 8` | 进流程日志 + 催一句，最多 2 次（`agentStallNudges`） |
| **读太多**（查过多少处**不同的东西**，同文件读第二遍不加数） | `agentExploreBudget: 25` | 催它「挑最可能的那个文件动手」，最多 2 次（`agentExploreNudges`）；**一旦开始改文件就彻底不再念** |

「读太多」数的是**不同目标**而不是调用次数：同一个文件读三遍、同一个关键词搜十几遍
在旧口径下会把预算瞬间烧光（实测某张票探索 82 次只有 22 个不同目标，73% 是重复），
而重复本身恰恰是最该被提醒的那件事 —— 所以催办话术会把重复量单独说出来
（「其中 N 次是在重看同一处」）。预算按项目可覆盖，见下方 FAQ。

两条都**只催不杀**，真正的兜底是 `ticketTimeoutMinutes`（整票硬超时，缺省 40 分钟）。
催办话术说的都是触发它的那个事实本身 —— 停滞催办说「多久没动」，探索催办说「读了几次」，
不会张冠李戴。

探索催办还有一条硬规矩：**它一旦开始改文件就不再提预算**。这件事是单向的 —— agent 的真实
节奏是「改一会儿 → 读一会儿确认 → 再改」，如果只在「这一轮恰好看到文件有改动」时才放过它，
那它每回去读代码确认就被念一次。所以判据记的是「有没有开始改过」，不是「这一轮有没有在改」。
同理，同一批探索**不会催第二遍**：催过的量会被记下来当门坎，只有它真的又往前读了新的东西
才可能再提醒。早期版本在这两处都错过一次，表现为同一张票反复收到一模一样的催办。

两条判据**同时成立时只发一条**。停滞看的是时间、探索看的是动作数，它们经常在同一秒一起
成立 —— 一次唤醒发两条长消息，每条都让它把同样的三步动作再做一遍，既占上下文也把「催办」
变成噪音。现在两个判据只判、不自己发，出口收在一个地方：两条都成立就合成一条
（开头一句话把两个事实都交代掉 → 一句结论 → **只留一份**动作清单），只成立一条就发那一条。
所以「2 条排队消息」里不该再出现两条长催办了；如果还看到，说明宿主跑的仍是旧代码。

#### 它会记住这个项目里同类问题改过哪些文件

一张票**跑成功**后，插件会把「工单里的关键词 → 这次实际改动的文件」记下来（项目级，
存在本地存储的 `memory` 表里，**`pipeline_forget` 清掉票据记录也不会清掉它**）。
下一张同模块的票，任务书里会多一节：

> ## 这个项目里同类问题的历史
> - 上次处理同类问题（工单 reczz…）改的是 `a.java`、`b.vue` —— 可以从这几个文件开始找，但不一定还是它们。

三个边界值得知道：只记**成功**的票（失败票的改动不可信）；措辞里明确写「不一定还是它们」，
它是起点不是答案；记忆写入失败**不影响交付**，只记一条日志。

#### 同一张票重跑时，它接着上一轮的会话继续

一张票跑失败、你重开它，插件**不再从零开始**：它会找回这张票上一轮用过的会话，
在那个会话里继续（前一轮读过的文件、摸清的页面位置都还在它的上下文里）。时间线的
「创建会话」那一站会写成 `会话 ticket-pms-sh-row-82-…（续接上一轮）`。

实测依据：`sh-row-82` 重开第二轮仍探了 57 次索，其中 5 个文件第一轮刚读过，而第二轮
总共才读 11 个 —— 不续接就是把同一段探索重走一遍。

三件事它会自己处理，你不用管：

- **会话 id 是一拿到就存下来的**：不是等这一轮跑完才记。所以哪怕你在它跑到一半时
  改了插件配置、宿主要重新加载插件，它下次也能认出上一轮的会话接着用 —— 不会在同一个
  工作区里留下两条同名会话（2026-11-17 撞过一次，见功能清单 §1.53）。
- **续接不上就自动新建**：宿主没挂会话持久化、那个会话被删了、header 坏了 —— 一条都不会
  让这张票跑不了，只是本轮从零开始。日志里会明确写「续接上一轮会话失败，改为新建」，
  不会静默降级。
- **老宿主没有这个能力**：直接新建，票照跑。
- **新票本来就没有下一轮**：行为与以前完全一致。

#### 失败了，点「接着跑」只补上没做完的那一步

票失败之后，明细里会多出两行：

```
卡在哪一步：提交（第 7 站「⑦ 提交（本地提交 / PR）」）
怎么接着跑：pipeline_reset 会从这一步继续，不用从头再来（同一个会话接着用）
```

「卡在哪一步」写的是**你要做的事**（改代码 / 跑验证 / 提交 / 回填表格 / 发通知），
不是内部的阶段名 —— 所以「提交失败」不会写成「mr-opening 失败」。

这时行尾的按钮会从「重跑」变成「接着跑」：

- **⑤ 改代码**倒下 → 仍然要 agent，仍然要重跑验证（代码没改完，后面对了也白搭）。
- **⑥ 跑验证**倒下 → 仍然要 agent（可能要看着报错再改一笔）。
- **⑦ 提交**倒下 → **不重新起会话、不重跑验证**，直接用上一轮改好的文件和上一轮的验证结论补一次提交。
  这一点很多人会以为它偷懒 —— 明细里会写「沿用上一轮的验证结论（…）；这一轮没有再跑一遍」。
- 实在要从头来：`pipeline_reset` 带 `from: "begin"`。

续跑用的还是**原来那个会话**，所以你可以在 GUI 里点进去接着追问。

> 早期版本没有这个能力：点「重跑」等于把票当新的，⑤ 会重新探索几十分钟。

### 「跑完了」≠「东西到你手上了」

`done` 只说明执行器认为活干完了。三件事各有各的失败方式，插件单独记成**交付维度**：

| 交付项 | 没做成时 |
|---|---|
| 改动（本地提交 / MR） | 工单面仍写「已完成」，但交付里点名「既没有本地提交也没有 MR」 |
| 回填表格 | 标题行加后缀「（表格未回写）」，正文里多一行「回填表格：没写成 —— 原因」 |
| 发通知 | 状态页看得见，不会假装一切正常 |

`pipeline_status` 会在全库分布下面多一行 `交付未完成：N 张`。回填失败分两种：**不值得再试的**（同步表 / 表里少列 / 只有读权限 / 那一行已被删）当场放弃并明说「这不是再试一次能好的」；**值得再试的**（网络、限流）留着待办，下次启动补做一次。

### 表格会怎么变

跑成 `done` / `skipped` 后回填三列：「是否处理」→ `writeBackStatus` 的值（缺省 `是`）、「处理结果」→ 结构化正文（改了什么一句话、验证结论、提交 sha/分支、处理会话、**末行记录号 —— 要重跑就复制它**）、「处理日期」→ 当天。**失败的工单缺省不回填**；打开 `writeBackOnFailure` 后只写「处理结果」一列，「是否处理」与「处理日期」绝不碰 —— 那两列填了就等于对看板说「处理完了」。不想让它动真表就把 `writeBack` 关掉。

## 排障

先跑 **`pipeline_doctor`**（或面板「体检」）。它把问题分三档：**阻断**（不修就跑不了工单）/**必须修复**（能跑但结果不对）/ **提醒**。飞书权限、版本发布、协作者、通知通道缺字段、插件版本落后 —— 都只在这里看得见，而且每条带具体修法。

| 现象 | 处理 |
|---|---|
| 一张工单都收不到 | 先看体检的阻断项；**再看体检「状态值」那一行**。它分两种说法，别搞混：① **`ℹ️ 表里现在没有待办的票`** —— 表里只有「是 / 否 / 已完成」这类已经处理过的取值，**这没坏**，收 0 张是对的。要让票进来，把新写那行的「是否处理」填成 `处理中` 就行。② **`⚠️ 状态值对不上`** —— 表里的取值既不是配置认的、也不是任何「已处理」的取值（比如填的是「待处理」），这才是配置错，按它给的修法改 `match.statusValues`（面板「工单表」组的「在处理中的状态值」）。**千万别为了「让体检变绿」把状态值改成「是」** —— 那会把已经处理完的行全部重收一遍并重跑 |
| 扫描跑了，但一张新票都没进来，界面上什么错都没有 | 这是最静默的一种失败，先查两个地方：① **项目卡片里的定位参数是否自相矛盾** —— `tableId`（多维表格的数据表）与 `sheetId`（电子表格的工作表）不该同时存在，它们是两种表型各自的坐标；体检的「提醒」里现在会点名这种组合。② **表型是不是被一个旧 `tableId` 抢走了**（历史 bug，已修）：`appToken` 里放的是电子表格的 wiki token、却还留着多维表格的 `tableId` 时，旧版会直接按多维表格读、报 `WrongBaseToken`，而体检因为不认 `tableId` 反而是绿的。最省事的做法：在项目卡片最上面的「工单表链接」里把链接重贴一次 —— 宿主会顺手清掉另一套坐标 |
| 带截图的工单跑到「处理工单问题」这一步就失败，报 `Cannot read properties of undefined (reading 'attachmentId')` | 这是**我们传给宿主的消息块结构**不对，不是你的配置问题。宿主认的图片块是 `{ type: 'image', attachment: {…} }`，插件旧版写成 `{ type: 'image', image: {…} }` ⇒ 宿主取 `block.attachment.attachmentId` 时崩。**升级到 2026-11-11 深夜之后的版本**即可（`sh-row-81` 那次事故）。没截图的票不受影响，所以它看起来像「偶发」 |
| 扫表失败，报 `match.sheetName="…" 没匹配到任何工作表。现有工作表：Sheet1 [sh…]` | 那一格填的是**文档标题**（浏览器标签页上那个名字），而它要的是**工作表（页签）名字** —— 电子表格里通常就叫 `Sheet1`。改法二选一：把 `match.sheetName` 改成报错里列出的那个页签名，或者干脆留空（取第一张可见工作表）。**2026-11-13 起**：如果填的确实是文档标题、且这张文档只有一张可见表，插件会自动降级用那一张并提示（多张可见表则报错不猜）；同时体检与「测这张表」也会把这条判成 ❌，不会再出现「体检全绿、扫票失败」 |
| 收不到任何工单且表里有数据 | 列名对不上。电子表格用 `match.sheetColumns`、多维表格用 `match.columns` 覆盖；插件现在会**当场报错并列出表里实际的列名**，不再静默扫出 0 张 |
| 四张票全倒在「⑦ 提交」，而改代码、跑验证都是 ✓ | 2026-11-18 修掉的一类真 bug：提交说明经 `git commit -m <说明>` 进命令行，说明里只要有英文双引号（工单序号是公式时一定会有）或撇号，**Windows PowerShell 5.1 就会把它按空格拆成多段 pathspec**，git 报一串 `error: pathspec '…' did not match any file(s)`。现在说明改走 `git commit -F <临时文件>`，完全不经过 shell。升级到 2026-11-18 之后的版本，老票点「接着跑」会只重做提交这一步 |
| 工单卡住 / 改错了想重来 | `pipeline_reset` 带 recordId，或面板「运行」页签点「重跑」。**推荐这条路**：只把失败的工单放回队列，不动内容 |
| 想让一张已完成的工单连内容一起重做 | 把「是否处理」拨走再拨回 `处理中` —— 会**整票重做并覆盖旧回填**，谨慎用 |
| 正在跑，想停 | `pipeline_cancel`，或面板「取消当前」 |
| 长时间没动静 | 看流程日志里的「这一站已经跑了 X」与心跳；超 40 分钟是单票超时，会自动通知 |
| 截图没进 prompt | 转 needs-info 并通知；补图后拨回重跑 |
| 表格没回填 / 显示「（表格未回写）」 | 多半是应用只有**读**权限（`code 91403`）。改成读写 → **重新发布版本** → 确认是**可编辑**协作者。若是「同步表」，飞书结构上就不允许改行，再试也没用 |
| 飞书报 `1254043` / `91403` | 表不存在，或应用不是协作者。用「添加文档应用」加成**可编辑** |
| 飞书报 `10014` | App ID / App Secret 不匹配。重新复制一遍凭据 |
| 报 `git fetch 失败：couldn't find remote ref main` | 主分支不叫 `main`。显式填 `repo.baseBranch` |
| 报「项目工作区目录不存在」 | `repo.path` 指向的目录不存在。插件不替你克隆 |
| 想看改动细节 | 通知里有工作区路径，`git show <sha>` 看那次本地提交（保留 24 小时） |
| 想接着问那一轮 | `pipeline_status` 里每张工单有 `处理会话：<sessionId>`，到会话列表点进去 |

> 排障时**先看体检，再看状态，最后才去翻代码**。三档体检把「跑不了」和「跑得不好」分开，
> 能省掉大半瞎找。

## FAQ

**Q：为什么我配了凭据还是报 auth 错？** 飞书授权必须**人工**把应用加成表格协作者（见快速开始第 3 步）；空字符串凭据会被当成「没配」。

**Q：凭据填好了，点了「保存」却什么都没发生？** 这是 2026-11-11 修掉的一个真 bug：`onSave()` 先算配置改动，为空就直接返回，写凭据那段在返回之后 —— 于是「只填凭据、不改配置」时一个字节都写不进去，面板还回一句「没有需要保存的改动」，而页签上又挂着「未保存 1 项」。现在凭据与配置是两条互不阻塞的通道，只填凭据也能存。如果还遇到，先看页签下面那行状态文案（成功会写「`KEY` 已保存」）。

**Q：配置是手填 JSON 吗？** 不用。常规做法是在设置面板点着改，无需抄任何 JSON。手改 `cordis.patch.yml` 仍然有效 （那是 **YAML**，改完必须重启宿主），只是不再是必经步骤。

**Q：工单表是「电子表格」不是「多维表格」，能用吗？** 能。插件自己判断表型，你不用填。只需额外开 `sheets:spreadsheet`（**读写** —— 只读够读工单， 但跑完回填会被拒，而那时工单已经是「完成」，你只会看到表格没更新）+ 加成**可编辑**协作者 + 重新发布版本。回填时按序号列**重新定位行**，中间插行也不会写错格子。

**Q：列名跟插件默认的对不上怎么办？** 先试别名（「问题描述」也认「缺陷描述」「问题」「Bug 描述」，「是否处理」也认「处理状态」「状态」）。 别名都不沾边就覆盖个别列：电子表格用 `match.sheetColumns`、多维表格用 `match.columns`， 写成一行 `description=我自己的描述列, status=我的状态列`。必需的两列是描述与状态。

**Q：电子表格没有 `record_id`，怎么认出「还是那张工单」？** 靠**序号列**（缺省取表头叫「序号」的那列）。**别在数据上方插行**、别重填序号 —— 序号留空时插件兜底用物理行号，那张工单在插行后会被判成新工单。

**Q：改了表里的内容，为什么工单没更新？** 只有「是否处理 = 处理中」的行会被跟踪修订；管理列（处理人 / 处理结果）的变化不触发。

**Q：它老是读一堆文件不动手，能调吗？** 能，但先分清两个旋钮：`agentExploreBudget`（缺省 **25**，数的是查过多少处**不同的东西** —— 同一个文件读第二遍、同一个关键词再搜一遍都不加数）与 `agentStallWarnMinutes`（缺省 8，工作区文件这么多分钟没变就催），催办次数分别是 `agentExploreNudges` / `agentStallNudges`（缺省都是 2）。

**探索预算可以按项目单独配**：项目设置的「基本」组里有一格「探索预算」（在「显示全部字段」下），留空 = 用全局 25；大仓（几十万行 Java、多个模块）填 40–60，小仓填 15。宿主的校验只接受正整数，填错会在那一格上报错。改全局缺省则要动 `src/core/config.js` 的 `BUILTIN_LIMITS`，然后同步安装副本并完全重启宿主。注意 `agentExploreBudget` 那个数字**同时印在任务书里**（`core/prompt.js` 直接引用它渲染），所以文案与执行永远是同一个值 —— 不会再出现「任务书写 12、实际用了 169」那种两边各写一份、谁都没在数的情况。

**Q：为什么它不改我已经配好的验证命令？** 项目配置里的 `verify.build` / `verify.test` 会**原样写进任务书**，标题是「改完怎么验证」。如果两样都没配，任务书会明说「本项目没有配置验证命令，不用为了跑点什么去构建整个工程」—— 这时它不会去猜 `pom.xml` / `package.json`。实测过一次：没注入命令时它自己摸索跑了 12 次 mvn/npm（5.4 分钟），而真正配的验证是个两秒跑完的静态检查。

**Q：为什么提交这一步最容易失败？** 因为它是唯一一步要把**自由文本**（提交说明）交给 shell 的地方。
改代码、跑验证传的是路径与命令名，字符集可控；说明里有工单描述、有 `IF(COUNTA(...),"",ROW()-1)` 这种带双引号的公式序号，
一旦经 `-m` 拼进命令行，PowerShell 5.1 与 bash 的引号规则又**不可能同时满足**（三种转义法实测都有一边会破）。
所以现在说明写进 `os.tmpdir()` 的临时文件、用 `git commit -F <文件>` 交给 git —— 文本不进命令行，这个故障类别就消失了。
**教训**：别用「把这种字符换成另一种字符」绕开转义问题，那只是把故障形态换掉。

**Q：同一张工单能被两个进程同时处理吗？** 不能。租约机制（`leaseTtlMinutes`）保证单飞，被抢走的一方让出并记错误。

**Q：AI 会直接动我的 main 分支吗？** **缺省会。** 缺省模式就在工作区检出里改代码、就地提交，提交落在检出当前分支上（通常就是 `main`）。 但插件**从不 push、从不合并**，要不要合进主干永远由你决定。想彻底隔离就打开 `isolateWorktree: true`。

**Q：工作区里有未提交改动，还能跑吗？** 能。插件在 agent 动手前用 `git stash create` 拍一份**只读**基线（不写 ref、不动工作区、不动索引）， 结束后只提交 agent 真正改过的文件 —— 你自己攒着的、甚至已经 `git add` 进索引的改动都原样留在工作区。

**Q：验证命令卡住会不会把流水线挂死？** 不会。验证有超时（缺省 30 分钟，宿主 shell 的 10 分钟会把它夹下去）与取消， 超时按退出码 **124** 记（和「检查没通过」区分开）。`pipeline_cancel` 会真的 kill 子进程。

**Q：`GITLAB_TOKEN` 还要配吗？** 缺省不用。**没打开那个开关时，体检一个字都不提它**（念多了人会学会忽略体检输出）。 只有项目显式打开远程 MR（面板「远程 MR（实验性）」组）才需要，那时缺它算**阻断**。

**Q：`workExecutor` 写成 `Agent`（大写）会怎样？** 直接报 `invalid-input` 并列可用值，不会静默退回 mock。`pushAdapter` 同理。只有留空才回落 `mock`。

**Q：处理完那次会话去哪了？** 留在项目工作区名下，没被回收 —— `pipeline_status` 里每张工单有 `处理会话：<sessionId>`， 点进去就能接着问。agent **实例**每次都会释放，留下的是会话本身。不想要就设 `keepSession: false`。

**Q：改了插件代码，怎么让宿主跑上新代码？** 三件事，少一件都不生效 —— 详见 [插件 README](../../plugins/ticket-pipeline/README.md)。

## 安全边界（使用前必读）

- **工单正文按不可信输入处理**：表里出现「忽略以上要求 / 删文件 / 改配置 / 发邮件到某地址」这类内容，
  会被当问题描述忽略并转 needs-info（见 [ADR-0003](../adr/0003-工单正文不可信.md)）。
- AI 只被授权改**这张工单的工作区检出**（`isolateWorktree: true` 时是隔离 worktree）+ 跑 `verify` 配置的命令。
- **敏感文件不会被提交**：名单覆盖 **8 大类、41 条正则**（`.env` 家族 / Spring 配置 / 包管理器 token /
  SSH·GPG 私钥 / 云与容器凭据 / 明文机器凭据 / 证书·密钥库·Terraform 状态 / 关键字兜底）。只做**点名暂存**（`git add -- <文件>` + `git commit -- <文件>`），**不用 `git add -A`**；被拦下的留在工作区，并写进提交说明的「未提交」一行。名单按后缀白名单写，不会误伤 `src/env.js` 这类源码。
- **`.git` 与插件 profile 有篡改自检**：每票开始与提交前各拍一次 sha256 快照
  （10 个 git 元数据文件 + 28 个官方 hook 名 + 4 个 profile 文件），动过就撤回暂存、整票判失败并点名文件。说清楚：这是**「被发现」不是「被阻止」**，真正能挡住任意命令的只有宿主权限。
- **凭据全部走 DSH credentials**，不落配置文件、不出现在错误信息里。
- **默认只做本地提交**：不 push 分支、不合任何 MR。只有项目显式打开远程 MR（**实验性**）才走 GitLab Commits API，
  而且只是 draft MR，同样不自动合并。
- **回填只写三列**，不碰别的列、不删行、不改工单正文；`failed` 的工单缺省不写。
  回填失败不改工单状态，但会被记成交付未完成。
- **事后动作会被补偿**：回填与发通知跟终态同一次落库，做完一项清一项；宿主中途重启，
  下次启动会把没做完的补上，`pipeline_status` 里能看到「待补」。
- **插件调宿主 shell 的 git 与 verify 两个子进程以完整文件系统权限执行**。这不是疏忽：
  插件不是会话，不显式声明 `danger-full-access` 就连 `git fetch` 都会 `Permission denied`。这条旁路**只给 git 和 verify 用**，不用于执行工单正文里的任何命令。代价是跑票期间这两个子进程能写你的整台机器。详见 [architecture.md §12.1](./architecture.md)。
